# ADR-0008: Build status is CI-generated, never hand-typed; no CI job without a subject

- **Status:** Accepted
- **Approver:** Engineering Coordinator (within Ashley's delegated authority — see
  Context; not a Freeze Point, no Ashley signature required)
- **Date:** 2026-09-03
- **Evidence:** channel event `e4fe807b5f9f703e8f6347600280ef549e445b5d92f6ca9be9da7753405345a0`,
  2026-09-03T10:31:02Z.

## Context

Ashley asked the team to make "proper decisions" on licence, README, contributing,
code of conduct, security, governance, CI, branch protection and decision records, and
record them in `CLAUDE.md`/`AGENTS.md` (channel event
`5e4d410b5988dbf69139e7b162262ef6bd4e38a4ce3a01a9c8d43949fd104b6b`,
2026-09-03T10:29:19Z). Of that set, most were restatements of decisions already on
record (D2 licence, D3 branch protection, `decisions/0001` on ADR location, and
today's WP-19/WP-19a community-health-file work) — those are not re-recorded here; see
`docs/DECISION_REGISTER.md`.

**This ADR records the two items from that pass that are genuinely new rulings, not
restatements.** Both concern CI, and both were decided by the Engineering Coordinator
directly, under Ashley's own delegation of the CI decision.

Ashley separately asked that build status be kept transparent, and said doing so
"will be your responsibility... to update it as and when everything keeps changing
with each commit," addressed to whoever owns the sourcing mechanism (Memory & Knowledge
Manager's earlier proposal, same thread, event
`ff14b7eccaea48d8864ec942c037d1f6d7b9d247beb542d32100aeb9e79d2737`). The
Engineering Coordinator declined the manual reading of that instruction and ruled a
different mechanism instead — this ADR records that ruling, not the instruction it
revises.

## Decision

**1. The README's build-status content is generated by CI at build time, never typed
by a person.** Counts and pass/fail state are derived mechanically; phase and
Freeze-Point state are read from `decisions/` and `docs/PROJECT_FACTS.md`. Anything
genuinely narrative that cannot be generated goes in one clearly-dated paragraph, kept
separate from the generated table — never mixed into it.

**2. No CI job is added for a subject that does not yet exist.** A schema-validation,
ontology-validation or licence-compliance job does not get added to the pipeline until
there is something for it to actually examine. The existing pipeline (ruff → mypy →
pytest → build, `test` as the required status check) is unchanged by this ruling; it
states a constraint on what gets added to it going forward.

## Alternatives considered

- **Hand-maintained status table, updated by a person on each relevant commit** — the
  literal reading of Ashley's instruction. Rejected: a manually maintained table on a
  build-in-public repository, read most by exactly the audience (funders) least
  positioned to notice when it drifts, will go stale — not eventually, within about a
  week at this project's commit rate — and it will be wrong in public, in the file a
  funder reads first. The Engineering Coordinator judged this cost higher than the cost
  of overriding a literal reading of Ashley's own instruction, and said so before
  proceeding rather than silently substituting a different mechanism.
- **Placeholder CI jobs for future validation classes (schema, ontology, licence),
  stubbed now so the pipeline "already covers" them.** Rejected: a job that passes
  because there is nothing yet for it to check manufactures confidence rather than
  earning it — the same failure shape as an uncited claim, one layer down in the build
  system instead of in a document.

## Consequences

- **Not a Freeze Point.** Reversible by ordinary amendment; no migration required.
- **Critical-path dependency for Honey's WP-33** (the generation mechanism itself),
  dispatched after WP-18. **Correction, 2026-09-05:** this line originally named the
  package "WP-24" — the Coordinator re-dispatched the same mechanism under a new
  number without checking against this ADR first, and WP-33 (children 33a generator/CI,
  33b README restructure) is the identifier that actually ran and shipped, not a
  separate, lost package. WP-24 was its earlier working name in this document only;
  no such package was ever dispatched. Until WP-33 lands (held as of 2026-09-05
  pending Ashley's README clearance — `docs/OPEN_QUESTIONS.md` D16), no build-status
  table appears on the README — a generated table that doesn't exist yet is
  preferable to a hand-typed one that will drift.
- **README's status section, once built, is a pointer into `decisions/` and
  `docs/PROJECT_FACTS.md`, not a second copy of their contents** — the same
  authoritative-source discipline this project's own `docs/LESSONS.md` already
  documents for every other cross-document claim in this repository.
- **Decision item 2 constrains future CI work packages directly:** a work package
  proposing a new CI job must name the subject that job examines; "defence in depth"
  or "as a placeholder" is not sufficient justification on its own.
